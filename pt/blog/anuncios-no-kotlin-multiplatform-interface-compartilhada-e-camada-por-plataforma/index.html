Anúncios no Kotlin Multiplatform: interface e camada nativa

Por Nesim Razon, desenvolvedor mobile independente · 2026-11-23

#Android#iOS#Anúncios

Anúncios são a parte de um app Kotlin Multiplatform que não dá para compartilhar, porque os SDKs são nativos em cada lado. O que dá para compartilhar é tudo em volta deles: quando mostrar um anúncio, o que acontece se não houver nenhum e o que cada tela pode saber. É assim que meus apps pequenos de Android e iOS dividem esse trabalho, com nomes reais do código.

Uma interface pequena no código compartilhado

No Slinglings, o módulo compartilhado tem uma interface chamada GameServices. As telas Compose compartilhadas conhecem só essa interface e nada de AdMob. Seus membros se dividem em alguns grupos.

Um contêiner global guarda a implementação atual: Services.impl começa como NoServices, um objeto sem anúncios que, quando se pede um anúncio premiado, entrega a recompensa na hora. A activity do Android o substitui no onCreate por AndroidServices, que envolve AdMob, UMP, Play Billing e Firebase Analytics. Uma regra molda cada método: o callback sempre dispara. Se não há anúncio pronto, onDone é chamado imediatamente, então o jogo nunca espera por um anúncio.

  • adsRemoved, billingAvailable, removeAdsPrice: estado da compra para remover anúncios.
  • interstitialBeforeNext(totalSolved, onDone): chamado quando o jogador toca em Próximo depois de uma fase.
  • showRewarded(onReward, onUnavailable): um anúncio premiado que o jogador pede.
  • privacyOptionsRequired e showPrivacyOptions(): a entrada de opções de privacidade do GDPR nas configurações.
  • logLevelComplete e funções parecidas: eventos de análise.

Por que uma interface e não expect/actual

Nesses projetos também uso expect/actual, mas só em funções puras pequenas: systemLanguage no Slinglings, decodificação de imagem no Snowlings. Anúncios são diferentes por quatro motivos.

  • Um anúncio precisa de uma Activity no Android e de um UIViewController no iOS. Os dois só existem em tempo de execução, então uma declaração em tempo de compilação não tem onde se apoiar.
  • Uma interface pode ser trocada. NoServices atende pré-visualizações e testes unitários, e o CalisanAsistani tem NoAds para o mesmo fim.
  • Uma interface Kotlin é exportada para o Swift como protocolo. O SDK de anúncios do iOS fica no Swift e o módulo Kotlin nunca o importa.
  • O código compartilhado continua testável: as regras de frequência abaixo não precisam de um aparelho, só de contadores e de um relógio.

O ponto de entrada do iOS deixa a mesma ideia explícita. No CalisanAsistani a função MainViewController recebe um IosNativeServices que pode ser nulo, e a classe Kotlin IosAds o usa com chamada segura. Se você passar null, o app simplesmente roda sem anúncios.

Camada do Android: primeiro o consentimento, depois o SDK

No Android quem faz o trabalho é a classe AdMobAds, e a ordem segue a orientação do Google. Os anúncios não podem começar antes de o consentimento estar resolvido.

  • 1. requestConsentInfoUpdate atualiza o estado do consentimento.
  • 2. loadAndPresentIfRequired mostra o formulário UMP só onde a lei exige.
  • 3. Verifica-se canRequestAds. Se uma sessão anterior já guardou o consentimento, o SDK inicia sem esperar.
  • 4. Roda MobileAds.setRequestConfiguration e depois MobileAds.initialize, fora da thread principal.
  • 5. Quando a inicialização termina, carregam-se um anúncio intersticial e um premiado. Ao fechar cada um, o próximo é carregado.

O passo 4 traz uma lição em um comentário do código. O callback de initialize pode chegar na thread de quem chamou, mas carregar anúncios exige a thread principal. Na versão 1.1.0 isso causava travamentos ocasionais na abertura, com a mensagem de que devia ser chamado na thread principal da interface. A correção é enviar os carregamentos ao handler principal. Um anúncio premiado só entrega a recompensa depois de fechado, então o jogador vê o resultado ao voltar ao jogo.

IDs de teste no debug, IDs reais no release

Os IDs de blocos de anúncios não são secretos, mas misturar IDs de teste e reais é perigoso: clicar nos seus próprios anúncios reais pode fazer sua conta ser sinalizada. Os arquivos Gradle do Astrolings e do CalisanAsistani resolvem isso por construção.

  • Os builds debug sempre usam os IDs de teste públicos do Google.
  • Os builds release leem os valores reais de gradle.properties, com chaves como admob.app e admob.banner.
  • Se um valor real estiver faltando, a tarefa de release lança um erro e nenhum pacote para a loja é gerado, então anúncios de teste não chegam à loja por engano.
  • No debug, o UMP é instruído a agir como se o aparelho estivesse no EEE, com um ID de dispositivo de teste em hash, para testar o formulário de qualquer país.
  • Os celulares de casa são registrados com setTestDeviceIds, a partir de uma propriedade Gradle separada por vírgulas. No iOS, a mesma função é de uma lista AdMobTestDeviceIDs no Info.plist.

O lado do iOS: uma ponte em Swift

No iOS, um arquivo chamado NativeServices.swift implementa a interface Kotlin. No CalisanAsistani a interface se chama IosNativeServices e oferece poucos membros: logEvent, setAdsReadyListener, makeBannerView, bannerHeight, showInterstitialAd, privacyOptionsRequired e showPrivacyOptions. O app SwiftUI passa o objeto Swift para MainViewController, e a classe Kotlin IosAds o transforma na mesma interface Ads compartilhada que o Android usa.

O fluxo é o do Android: atualização do consentimento, formulário se necessário, depois início do MobileAds e pré-carga de um intersticial. Dois detalhes importam. A função start do Swift é chamada cerca de 0,6 segundo depois que a primeira tela aparece, porque o formulário de consentimento precisa de uma janela para ser apresentado. E o método do intersticial devolve um Boolean: true se mostrou um anúncio, false se nenhum estava pronto. Com false, o lado Kotlin chama onDone por conta própria.

  • Banner: um UIKitView do Compose cuja factory chama makeBannerView, com a altura vinda de bannerHeight.
  • O Astrolings usa só banner. O CalisanAsistani usa banner e intersticial.
  • O Slinglings no iOS ainda roda com NoServices. Os IDs de anúncios do iOS estão guardados no código, mas a parte Swift ainda não foi escrita.

Uma armadilha de nomes: a interface Ads do Kotlin e a interface vista pelo Swift não devem ter um método com o mesmo nome e assinatura diferente, porque o Swift reclama dos rótulos dos argumentos. Por isso o método visto pelo Swift se chama showInterstitialAd e não showInterstitial.

As regras de frequência vivem no código compartilhado

A política de quantas vezes mostrar um anúncio é Kotlin puro, então as duas plataformas recebem o mesmo. No CalisanAsistani o objeto AdPolicy fica em commonMain e usa uma fonte de tempo monotônica, então mudar o relógio do aparelho não serve para enganá-lo.

  • CalisanAsistani: nenhum anúncio nas 3 primeiras voltas à tela inicial, depois a cada 3 voltas e pelo menos 240 segundos depois do último anúncio. Nunca dentro de uma tela de cálculo.
  • Slinglings: nenhum anúncio nas primeiras 6 fases resolvidas, depois no máximo um a cada 3 fases, com pelo menos 90 segundos entre eles e até 8 por dia. Nunca durante o jogo, nos menus ou ao desfazer.
  • Anúncios premiados só quando o jogador pede, por exemplo quando as dicas acabam.
  • Os contadores vivem só no processo do app. Eles zeram quando o app reinicia.

Como as regras só dependem de contadores e do tempo, é fácil testá-las sem um aparelho. Uma regra que decide quando incomodar o jogador merece um teste.

Análise desde a primeira versão do iOS e depuração

Minha lista de verificação do iOS diz que Firebase Analytics e Crashlytics vêm com a primeira versão. A regra é de 14 de novembro de 2026, depois que o app de iOS do 2048 foi publicado sem eles. O app Swift chama FirebaseApp.configure primeiro, antes de qualquer outra coisa. O Crashlytics inicia sozinho e uma etapa do build envia os arquivos dSYM. O Kotlin envia os eventos pelo membro logEvent, com os mesmos nomes do Android. No CalisanAsistani nunca se envia salário, data ou outro valor pessoal.

Para depurar, o lado Android registra eventos de anúncios: loaded, shown, impression, clicked, dismissed. Um evento extra, resumed_no_dismiss, dispara quando o app volta ao primeiro plano e o SDK ainda diz que há um anúncio na tela. Foi assim que se flagrou um anúncio realmente travado em um celular. A história completa está no artigo Detectar um anúncio intersticial travado no Android com eventos. No iOS, o delegate do banner escreve uma linha curta com NSLog quando um anúncio chega ou falha, legível por USB.

Perguntas frequentes

Dá para chamar o SDK do AdMob direto do código comum do Kotlin?

Não como uma única chamada compartilhada. Os SDKs de Android e iOS são bibliotecas nativas separadas, então cada plataforma mantém sua própria camada atrás de uma interface compartilhada.

Por que não usar expect/actual para anúncios?

Anúncios precisam de uma Activity ou de um controlador de view que só existem em tempo de execução, e uma interface pode ser trocada por uma versão sem anúncios em testes e pré-visualizações.

Como evitar clicar nos próprios anúncios reais durante o desenvolvimento?

Os builds debug usam os IDs de teste do Google, o build release falha sem IDs reais e os dispositivos de teste são registrados no Android e no iOS.

Quando o formulário de consentimento deve aparecer?

Antes de qualquer solicitação de anúncio. Verifique o consentimento primeiro, mostre o formulário UMP se necessário e inicie o SDK de anúncios só quando canRequestAds for true.

As regras de anúncios também devem ser compartilhadas?

Sim. Manter a política de frequência em Kotlin comum dá o mesmo comportamento nas duas plataformas e permite testá-la com testes unitários.
