Kotlin Multiplatform: recursos da plataforma com interface nula

Por Nesim Razon, desenvolvedor mobile independente · 2026-11-26

#Android#iOS#Notas de desenvolvimento

Cedo ou tarde uma tela compartilhada em Kotlin precisa de algo que só uma plataforma tem: uma compra, um seletor de fotos, um salvamento na nuvem. A resposta comum é expect/actual. Nos meus próprios apps encontrei uma menor: dar ao código comum uma interface e deixar a propriedade ser nula quando a plataforma não consegue fazer aquilo. Mostro como isso fica em código real e onde deixa de servir.

O problema: um recurso que existe só de um lado

Meu app Astrolings é um projeto Kotlin Multiplatform com um app Android e outro iOS que compartilham uma única interface Compose. Quando o levei para o iOS, a versão Android já vendia uma compra para remover anúncios. Na primeira versão, a do iOS ainda não tinha esse produto definido na loja.

A tela compartilhada ainda precisava desenhar uma página de perfil, e essa página tem um botão de remover anúncios. A pergunta real era: como o código comum descobre que esse botão não deve existir nesta plataforma? Eu não queria verificações do nome da plataforma espalhadas pelas telas, nem uma compra falsa que não faz nada em silêncio.

A resposta no código: uma propriedade que pode ser nula

O módulo compartilhado declara uma interface pequena chamada RemoveAds. Ela tem dois membros: um preço, que é um texto que pode ser nulo, e uma função buy que devolve true se a tela de compra foi aberta. A interface Platform, que cada tela compartilhada recebe, tem então uma propriedade: removeAds, do tipo RemoveAds com ponto de interrogação.

No Android, essa propriedade devolve um objeto que encaminha para o código de cobrança. No iOS, a classe IosPlatform a deixa como null, com um comentário dizendo que o produto da loja não foi definido na primeira versão. Essa é toda a diferença entre as plataformas. Sem expect, sem actual, sem flag.

A tela compartilhada lê isso em um único lugar. Quem a chama passa um parâmetro chamado canRemoveAds, que é simplesmente removeAds diferente de null. Quando é falso, a página de perfil mostra uma frase tranquila dizendo que o app é gratuito e mostra um anúncio pequeno embaixo, em vez de um botão. Simplifiquei a descrição, mas os nomes vêm direto do projeto.

Por que não expect/actual

Nesses projetos também uso expect/actual, mas para funções puras pequenas. O Snowlings, por exemplo, declara uma para decodificar bytes de imagem em um bitmap e outra para converter um bitmap em PNG. As duas plataformas sempre conseguem fazer isso, então uma implementação ausente é simplesmente um erro de compilação, que é exatamente o que se quer.

Uma compra é diferente, por três motivos.

  • Precisa existir um actual para cada alvo. Se o iOS ainda não consegue comprar, o actual tem que mentir: devolver um preço falso ou não fazer nada quando chamado. Nada no tipo diz isso.
  • Ela precisa de estado e de uma tela. Uma compra real guarda uma conexão de cobrança e uma Activity. São objetos com ciclo de vida, e a declaração de uma função de nível superior é um lugar ruim para eles.
  • O código comum não consegue perguntar a uma função se ela é real. Com uma interface nula, uma única comparação com null responde, e o compilador obriga cada ponto de chamada a tratar a resposta.

Null, objeto nulo ou corpo padrão: a regra que uso

Uso três formas diferentes de dizer que uma plataforma não consegue fazer algo, e elas não são intercambiáveis. A escolha depende de uma pergunta: o que o usuário deve ver quando o recurso falta?

Se o usuário não deve ver nada diferente, exceto que a coisa simplesmente não acontece, uso um corpo padrão ou um objeto nulo. No Snowlings, a interface Platform dá ao salvamento na nuvem um corpo padrão vazio, e ao seletor de fotos um que informa que não há foto. Uma plataforma que não os sobrescreve simplesmente não faz nada. No Slinglings, um objeto pequeno chamado NoServices ocupa o lugar de anúncios e compras: não tem anúncios, e se um anúncio premiado é pedido, entrega a recompensa na hora. Como o callback sempre dispara, o jogo nunca espera.

Se o usuário deve ver uma tela diferente, uso null. Um botão escondido, um parágrafo diferente, uma entrada de menu que não existe. Aqui o null não é um erro. É a informação de que a tela compartilhada precisa para desenhar corretamente.

  • Callback que sempre deve disparar: objeto nulo, como NoServices.
  • Ação opcional sem nada para mostrar: corpo padrão, como o seletor de fotos.
  • Recurso que muda o que é desenhado: interface nula, como removeAds.

O Slinglings mostra o caso intermediário. Sua interface GameServices tem uma flag chamada billingAvailable e um preço que pode ser nulo. Funciona, mas a flag e a função buy podem se contradizer. Com o objeto nulo do Astrolings, não dá para chamar buy em algo que não existe.

Três estados, não dois

Uma capacidade nula tem uma armadilha: null pode significar coisas demais. Mantenho os significados separados colocando cada um em um lugar diferente.

Ausente nesta plataforma é o null da propriedade. Presente, mas sem permissão agora é uma pergunta separada sobre o objeto, como a verificação de permissão na interface de notificações. Presente, mas indisponível no momento é um valor que pode ser nulo dentro dele: em RemoveAds, um preço nulo significa que o produto não pode ser comprado neste momento, por exemplo porque a loja ainda não respondeu. A tela reage de forma diferente a cada um. O primeiro esconde o botão, o segundo pede permissão, o terceiro mostra o botão sem preço.

Se você junta os três em um único null, acaba depurando um botão que some e só aparece às vezes.

Os testes ficam mais fáceis

O código comum só enxerga uma interface, então um teste pode dar a ele a plataforma que quiser. No Astrolings, a pasta de testes tem um Platform falso, em um arquivo chamado IosShots, cujos membros não fazem nada e em que removeAds é null. Esse único falso permite rodar as telas como um teste unitário comum, sem celular e sem biblioteca de compras.

A mesma ideia dá o teste contrário de graça. Passe um objeto com preço e o botão aparece. Passe um que devolve false em buy e dá para verificar a mensagem de erro. Nos dois casos, a única coisa testada é a reação da tela compartilhada.

Compare com uma declaração actual: ela não pode ser trocada facilmente em um teste, porque é escolhida em tempo de compilação.

O lado do iOS: null na fronteira

A mesma ideia aparece um nível abaixo. No Snowlings e no Astrolings, o ponto de entrada do iOS é uma função Kotlin chamada MainViewController, e seu parâmetro é o objeto ponte do Swift, com ponto de interrogação no tipo. Na versão do IosPlatform do Snowlings, o salvamento na nuvem não faz nada se esse objeto falta, e o seletor de fotos responde que não há foto.

Uma ponte ausente significa, então, um app mais silencioso, não um travamento. Isso é útil durante uma migração, quando algumas peças em Swift ainda não estão escritas: o lado Kotlin continua rodando e dá para ver o que ainda falta.

Uma nota prática da minha lista de verificação de migração para iOS: a interface Platform compartilhada lista a capacidade nula de forma explícita, então uma migração nova começa perguntando, para cada membro, se esta plataforma já o tem.

Quero ser preciso sobre o que fiz e o que não fiz. Nesses apps o objeto Platform nunca é nulo, e no ponto de entrada a única coisa com tipo nulo é a ponte do Swift. A propriedade de capacidade nula existe no Astrolings. As demais capacidades usam corpos padrão ou o objeto nulo.

Onde dói

Capacidades nulas não são de graça.

  • Cada ponto de chamada precisa tratar o null. Esse é o objetivo, mas um recurso usado em dez lugares leva dez pontos de interrogação. Se doer, envolva a verificação em uma função pequena e chame essa.
  • O Kotlin exporta uma interface para o Swift como protocolo, e a anulabilidade passa como opcional. Funciona, mas só me apoio nisso no ponto de entrada, onde o tipo é simples.
  • Não use quando as plataformas são sempre iguais. Uma função que todos os alvos conseguem implementar pertence ao expect/actual ou a uma interface comum.
  • Não use para algo que quase sempre está presente. Se é null em uma plataforma de cem, os pontos de interrogação viram ruído.

Minha regra prática: quando a tela compartilhada precisa parecer diferente, a capacidade é nula. Quando só precisa continuar funcionando, dê a ela um padrão.

Perguntas frequentes

Quando uma interface nula é melhor que expect/actual?

Quando uma plataforma pode não ter o recurso e a tela compartilhada precisa parecer diferente sem ele. O expect/actual obriga cada alvo a fornecer algo, mesmo que falso.

Uma interface nula é o mesmo que o padrão de objeto nulo?

Não. Um objeto nulo finge que o recurso existe e não faz nada. Uma interface nula diz claramente que ele não existe, e o código comum pode esconder o botão ou mudar o texto.

Como testar código comum que depende de recursos da plataforma?

Escreva um Platform falso pequeno na pasta de testes. Devolva null na capacidade para testar o caso ausente, ou um objeto com preço para testar o caso presente.

Uma interface nula funciona pela ponte do Swift?

Nos meus apps a função de entrada do iOS recebe o objeto ponte do Swift como nulo, e o lado Kotlin não faz nada se ele falta. Não exportei para o Swift a propriedade de capacidade nula em si.

O que um null nunca deve significar?

Não use um único null para várias situações. Mantenha ausente nesta plataforma, sem permissão agora e indisponível no momento em três lugares separados.
