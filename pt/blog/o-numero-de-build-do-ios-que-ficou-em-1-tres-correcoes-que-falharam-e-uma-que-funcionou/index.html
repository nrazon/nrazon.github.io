O número de build do iOS que ficou em 1: três correções que falharam e uma que funcionou

Por Nesim Razon, desenvolvedor mobile independente · 2026-11-17

#Notas de desenvolvimento#iOS

Cada envio ao App Store Connect precisa de um número de build maior que o anterior. Nosso pipeline na nuvem continuava produzindo um pacote com número de build 1, não importava o que mudássemos. Foram necessárias três tentativas para descobrir o motivo. Esta é a história e a correção, para quem compila apps iOS a partir de um projeto Xcode gerado sem ter um Mac próprio.

O sintoma

A etapa de envio falhou com um erro dizendo que a versão do pacote deve ser maior que a enviada anteriormente. O primeiro envio de um app sempre funciona, então o problema só aparece a partir do segundo build. O número exibido para o build na loja era 1 todas as vezes.

Há dois números em jogo. A versão de marketing, como 1.0, é a que as pessoas veem. O número de build, CFBundleVersion, só precisa aumentar a cada envio da mesma versão de marketing.

Primeira tentativa: opções do arquivamento

A ferramenta de build permite passar opções extras ao comando de arquivamento, então passamos o número de build ali. Nada mudou. A opção foi aceita sem efeito algum sobre o valor que acabava no pacote.

Segunda tentativa: editar a descrição do projeto

O projeto é gerado pelo XcodeGen a partir de um pequeno arquivo de descrição, que tem um campo para o número de build. Reescrevemos esse campo com sed antes de gerar o projeto, usando o número da execução da integração contínua. O projeto gerado continha o valor novo, mas o pacote ainda dizia 1.

O motivo é que o Info.plist produzido pelo XcodeGen não pega o número de build dessa configuração. Ele tem seu próprio valor, e é esse que é empacotado.

Terceira tentativa e uma ideia melhor

Uma terceira variação da mesma ideia falhou do mesmo jeito. O que precisava mudar não eram as configurações de build, e sim o arquivo que realmente é lido: o Info.plist.

A correção: escrever no Info.plist

Depois que o projeto é gerado, um único comando define o valor diretamente: PlistBuddy com Set :CFBundleVersion e o número. O número é 1000 mais o contador de builds do serviço de integração contínua, então sempre cresce e não colide com envios anteriores.

A segunda metade da correção é provar. Antes de enviar, o script lê o CFBundleVersion do pacote pronto e o imprime no log. Se o valor estiver errado, você vê em um minuto, e não depois de um envio com falha.

O que levar

  • Defina o número de build no arquivo que é empacotado, não numa configuração que talvez não chegue a ele.
  • Imprima o valor do pacote final, não o da sua entrada.
  • Use um contador que só sobe, como o número de build da integração contínua com um deslocamento fixo.
  • Se o envio disser que a versão do pacote deve ser maior, olhe primeiro o pacote.

Perguntas frequentes

Qual é a diferença entre a versão e o número de build?

A versão é o número que os usuários veem, por exemplo 1.0. O número de build só precisa subir a cada envio dessa versão.

Por que editar a descrição do projeto não funcionou?

O Info.plist gerado pelo XcodeGen não pegou o número de build dessa configuração, então o pacote manteve seu próprio valor.

Como verificar o valor empacotado?

Lê-se o CFBundleVersion do Info.plist dentro do pacote pronto e imprime-se no log de build antes de enviar.
