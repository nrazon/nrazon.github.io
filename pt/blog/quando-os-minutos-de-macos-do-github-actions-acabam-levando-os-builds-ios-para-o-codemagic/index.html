Sem minutos de macOS no GitHub Actions: migrando para o Codemagic

Por Nesim Razon, desenvolvedor mobile independente · 2026-11-23

#iOS#Notas de desenvolvimento

Compilo meus apps de iOS a partir de um notebook com Windows, então cada build roda em um Mac alugado. Por um tempo esse Mac veio do GitHub Actions. Depois o crédito gratuito chegou perto do fim e passei o trabalho novo para o Codemagic. Aqui estão os números reais, as diferenças entre os dois fluxos e os hábitos que evitam ficar sem minutos.

Por que a cota importa: um minuto não é um minuto

No GitHub Actions o que é gratuito é dinheiro, não minutos. Segundo a documentação de cobrança do GitHub, o plano Free inclui 12 USD de computação por mês para repositórios privados, e um runner de macOS custa 0,062 USD por minuto. Um runner Linux de 2 núcleos custa 0,006 USD, então um minuto de macOS é cerca de dez vezes mais caro. O GitHub também arredonda cada job para o minuto inteiro.

Conta simples: 12 dividido por 0,062 dá cerca de 193 minutos de macOS por mês. Meu primeiro dia completo de testes gastou 54 deles, ou seja, 3,35 USD. Em 14 de novembro o crédito estava perto de 90 por cento usado e decidi que os apps novos seriam compilados em outro lugar.

Os dois fluxos lado a lado

  • GitHub Actions: arquivo .github/workflows/ios.yml, runner macos-26, disparado por um push na branch ios-kmp quando iosApp, shared ou os arquivos do Gradle mudam. O número do build vem de github.run_number.
  • Codemagic: arquivo codemagic.yaml na raiz do repositório, tipo de instância mac_mini_m2, iniciado à mão pela página web (Start new build, branch main, escolher o fluxo). O número do build é 1000 mais o número de build do Codemagic.
  • Os dois têm dois jobs: um build sem assinatura para o simulador como verificação rápida, e um job de TestFlight que arquiva, assina e envia.
  • Os dois têm limite de tempo: 40 minutos para o simulador e 60 para o TestFlight (timeout-minutes em um, max_build_duration no outro).
  • Segredos: segredos do repositório no GitHub, e no Codemagic um grupo de variáveis chamado apple. Ambos guardam o mesmo id da chave, o id do emissor e o texto da chave do App Store Connect.

Quanto custa um build em cada lado

Na minha configuração, uma execução de TestFlight no GitHub levou cerca de seis minutos, ou seja, uns 0,37 USD. Com 12 USD são cerca de 32 execuções por mês, se eu não fizesse mais nada. No Codemagic minhas notas registram builds de uns 8 a 10 minutos.

A página de preços do Codemagic diz que pessoas físicas recebem 500 minutos grátis por mês em máquinas macOS M2 com uma conta pessoal, zerados no dia um de cada mês. Além disso, a página lista 0,095 USD por minuto para a VM macOS M2. Com 8 a 10 minutos por build, 500 minutos são de 50 a 60 builds. Cada um é mais lento, mas o balde é bem maior para essa carga de trabalho.

Os preços mudam. Confira as páginas de preços atuais do GitHub e do Codemagic antes de planejar com esses números.

Um exemplo ajuda. Suponha que um app novo precise de cinco execuções com falha antes do primeiro bom build de TestFlight, de uns dez minutos cada. É um exemplo, não um registro meu.

  • Crédito no GitHub: 12 USD, cerca de 193 minutos de macOS.
  • Uma execução de TestFlight no GitHub: uns 6 minutos, 0,37 USD.
  • Cinco execuções com falha mais uma boa de 10 minutos: 60 minutos. No Codemagic isso é 12 por cento dos 500 grátis.
  • No GitHub esses mesmos 60 minutos a 0,062 USD seriam 3,72 USD, quase um terço do crédito mensal.
  • Os 500 minutos grátis do Codemagic na tarifa de pagamento por uso de 0,095 USD seriam 47,50 USD, então o balde gratuito vale dinheiro de verdade.

O ponto é que as falhas, não os acertos, decidem a rapidez com que o balde esvazia.

Migrando um repositório: o que muda

O job do simulador migrou quase sem mudanças: XcodeGen e depois xcodebuild com CODE_SIGNING_ALLOWED=NO. O job de TestFlight precisou de mudanças reais, porque o Codemagic tem suas próprias ferramentas de assinatura.

O job do Codemagic reconstrói o arquivo da chave de API, cria um chaveiro, baixa os arquivos de assinatura e depois gera o ipa e o publica:

  • keychain initialize
  • app-store-connect fetch-signing-files "com.example.app" --type IOS_APP_STORE --create
  • keychain add-certificates
  • xcode-project use-profiles
  • xcode-project build-ipa --project iosApp/iosApp.xcodeproj --scheme iosApp
  • app-store-connect publish --path build/ios/ipa/iosApp.ipa

O número do build também pediu cuidado. Na minha configuração o número no pacote ficou em 1 até eu escrevê-lo direto no Info.plist com PlistBuddy depois de gerar o projeto. Os detalhes da assinatura têm um post próprio sobre certificados de assinatura na nuvem, e o número do build também tem o seu.

Erros que queimaram minutos

A maior parte dos meus minutos perdidos veio de três erros, não do preço. Cada um é barato de evitar quando você o conhece.

  • A assinatura na nuvem durante a etapa de arquivamento criou um certificado Apple Development novo a cada build. Depois de uns onze, a conta atingiu o limite de certificados e os builds falharam. A solução foi uma única chave de distribuição que eu guardo, baixada com as ferramentas de assinatura mostradas acima.
  • O número do build ficou em 1 por três tentativas. Três execuções, uns trinta minutos, por uma linha no Info.plist.
  • Um Bundle ID errado escolhido no formulário do App Store Connect fez o envio falhar com um erro do altool. Dá para conferir o Bundle ID pela API do App Store Connect antes de qualquer build, e isso custa zero minutos de macOS.

A regra que tirei disso: tudo que o Windows ou uma página web puder verificar vem antes do Mac. Uma execução que falha custa o mesmo que uma que dá certo.

Hábitos que economizam minutos

  • Rode primeiro no Windows a compilação de Kotlin para iOS: o alvo do simulador compila localmente e não gasta tempo de macOS.
  • Passe um pequeno script de verificação no projeto antes de enviar, para pegar as armadilhas que já me custaram execuções.
  • No GitHub, limite o gatilho com paths para que uma mudança em um README não ligue um Mac.
  • Use uma marca na mensagem do commit. Um commit com [testflight] roda só o job de TestFlight e pula o do simulador.
  • Use concurrency com cancel-in-progress, para que um push novo cancele a execução anterior.
  • No Codemagic, inicie os builds só à mão. Um push nunca gasta minutos por acidente.
  • Rode sempre primeiro o fluxo do simulador e o de TestFlight só quando ele passar.

Planejando o mês

Meu plano é simples. O crédito do GitHub renova no começo do mês, e os 500 minutos do Codemagic também. Apps novos e sessões longas de portagem vão para o Codemagic. O GitHub fica com os repositórios antigos que já têm um fluxo funcionando.

Conto em builds, não em minutos: uns 8 a 10 minutos cada, mais uma folga para a primeira execução de um app novo, quando as falhas são mais prováveis. Se o mês parece apertado, trabalho mais no Windows e envio menos builds, mas mais bem preparados.

Não há um vencedor único. O GitHub Actions é cômodo quando o código já está lá: o fluxo fica no repositório, os segredos estão nas configurações dele e o build pode começar a cada push. Seu ponto fraco para mim é o crédito em dólares, porque um minuto de macOS o consome dez vezes mais rápido que um de Linux.

O Codemagic combina com um repositório que compila iOS raramente e à mão. Os minutos são um balde à parte de 500 e as ferramentas de assinatura foram feitas para o caminho até o TestFlight. Seu ponto fraco é montar mais uma conta, mais um grupo de variáveis e mais um lugar para os segredos.

Se você compila iOS algumas vezes por semana, os dois servem. Se está portando vários apps no mesmo mês, conte primeiro os builds e escolha o balde mais barato.

Perguntas frequentes

Quanto custa um minuto de macOS no GitHub Actions?

A página de cobrança do GitHub lista 0,062 USD por minuto para o runner de macOS, contra 0,006 USD para um runner Linux de 2 núcleos. Consulte a página para ver os preços atuais.

Quantos minutos grátis o Codemagic dá?

A página de preços diz que pessoas físicas recebem 500 minutos grátis por mês em máquinas macOS M2 com uma conta pessoal, zerados no dia um do mês.

Os minutos do GitHub Actions são grátis em repositórios públicos?

A documentação do GitHub diz que os runners padrão hospedados pelo GitHub são gratuitos em repositórios públicos. O crédito que descrevo vale para os privados.

Posso usar os dois serviços ao mesmo tempo?

Sim. Mantive os fluxos do GitHub nos repositórios antigos e usei o Codemagic nos apps novos. Cada repositório usa um dos dois.
