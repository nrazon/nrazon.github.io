Ler o Crashlytics com um assistente de código com IA: a armadilha da pasta do projeto

Por Nesim Razon, desenvolvedor mobile independente · 2026-11-20

#Notas de desenvolvimento#Android

Se o seu assistente de código com IA está conectado ao servidor MCP do Firebase mas não enxerga nenhuma ferramenta do Crashlytics, a causa provavelmente é a pasta do projeto e não um login quebrado. O servidor liga as ferramentas de acordo com os SDKs do Firebase que encontra na pasta para a qual aponta. Se você apontar para um app Android que usa o Crashlytics, as ferramentas aparecem. Aqui conto como descobri isso e o que verifico antes de confiar em um relatório.

O sintoma

Pedi ao assistente que olhasse os relatórios de falhas de alguns apps. Ele conseguia listar apps e ler detalhes do projeto, mas não havia nenhuma ferramenta do Crashlytics. Reconectar o servidor e entrar de novo não mudou nada, e o login estava certo, pois outras ferramentas do Firebase funcionavam.

A causa: as ferramentas seguem a pasta do projeto

O servidor MCP do Firebase ativa algumas ferramentas automaticamente com base nos SDKs do Firebase que detecta no diretório do projeto que usa. Meu diretório padrão tinha uma pequena configuração do Firebase de um projeto de painel que não tem o SDK do Crashlytics, então o servidor nunca ofereceu as ferramentas do Crashlytics.

A correção sem editar arquivos de configuração

O ambiente pode ser alterado de dentro da sessão. Chamei a ferramenta de atualização do ambiente com o diretório do projeto apontando para a pasta de um app Android que usa o Crashlytics, junto com o projeto do Firebase desse app. Depois, procurar “crashlytics” na lista de ferramentas devolveu as de relatórios e problemas. Nenhum arquivo de configurações foi tocado.

Leia o guia antes do primeiro relatório

O servidor também publica um guia como recurso, com a forma correta de pedir relatórios. Lê-lo primeiro me poupou de adivinhar filtros. É uma leitura curta e explica quais tipos de relatório existem e o que cada um precisa.

Confira o projeto ativo toda vez

As ferramentas agem sobre o projeto ativo do Firebase. Uma vez criei um app no projeto errado porque o ativo era diferente do que eu supunha. Agora, antes de qualquer ação de escrita, peço ao servidor o ambiente atual e comparo o identificador do projeto com o que eu quero.

Não leia um erro como “sem falhas”

Um app devolveu 404 quando pedi seus principais problemas. Isso não significava zero falhas. Nesse app a coleta de dados de falhas está desativada de propósito, então não há nada para ler. Um relatório só faz sentido se a coleta estiver ativa para o app e para a versão que importa, por isso anoto quais apps estão cobertos antes de dizer que uma versão está limpa.

Lista de verificação

  • Sem ferramentas do Crashlytics? Aponte o servidor para uma pasta de app que contenha o SDK do Crashlytics.
  • Defina o diretório do projeto e o projeto ativo em uma só atualização do ambiente e confirme os dois.
  • Leia o recurso do guia de relatórios antes de pedir dados.
  • Confirme o projeto ativo antes de criar ou alterar algo.
  • Saiba quais apps têm a coleta ativada, para não confundir um resultado vazio com um limpo.

Perguntas frequentes

Por que o servidor MCP do Firebase não mostra ferramentas do Crashlytics?

O servidor ativa as ferramentas com base nos SDKs do Firebase que encontra no seu diretório de projeto. Se essa pasta não tem o SDK do Crashlytics, as ferramentas do Crashlytics ficam ocultas.

Como faço as ferramentas do Crashlytics aparecerem?

Atualize o ambiente do servidor para que o diretório do projeto seja uma pasta de app que usa o Crashlytics e defina o projeto do Firebase correspondente. Depois procure de novo na lista de ferramentas.

Um 404 nos principais problemas significa que o app não tem falhas?

Não. Pode significar que a coleta de falhas está desativada nesse app, então não há dados para devolver.

Preciso editar um arquivo de configuração?

Não necessariamente. A ferramenta de atualização do ambiente pode mudar o diretório e o projeto ativo durante a sessão.
