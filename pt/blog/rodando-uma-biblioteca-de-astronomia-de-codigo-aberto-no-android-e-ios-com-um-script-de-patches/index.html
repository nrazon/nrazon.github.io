Astronomia de código aberto no Android e iOS com um script de patches

Por Nesim Razon, desenvolvedor mobile independente · 2026-11-18

#Notas de desenvolvimento#Astronomia#iOS

Nosso app de horóscopo e Lua precisa de astronomia de verdade: onde está a Lua, quando muda a fase, quando um planeta parece andar para trás. Para isso usamos um motor de código aberto, e ele funcionava no Android. Quando passamos o app para Kotlin Multiplatform para o iPhone, o motor não veio junto. Foi assim que o fizemos rodar nas duas plataformas sem mudar um único cálculo.

O problema: um artefato só para JVM

O motor é publicado como uma biblioteca Kotlin, e a versão pronta do repositório central do Maven funciona apenas na máquina virtual Java. Isso é ótimo no Android e inútil no código compartilhado, que também precisa compilar para o iPhone. Não queríamos reescrever milhares de linhas de matemática orbital, nem chamar uma biblioteca diferente em cada plataforma, porque dois motores podem dar horários de fases da Lua ligeiramente diferentes.

Usar o código-fonte, não o pacote

O motor é de código aberto com licença MIT e inteiro está em um único arquivo-fonte Kotlin. Então, em vez do pacote, pegamos o próprio arquivo-fonte e o colocamos no conjunto de fontes comum do módulo compartilhado. A pergunta passou a ser o que há de específico de Java nesse arquivo. Descobrimos que muito pouco.

O que precisou mudar

  • Uma anotação em nível de arquivo que define o nome da classe Java, que o código comum não conhece.
  • Algumas anotações que tornam as funções estáticas ou geram sobrecargas Java, de novo só de Java. Removê-las não muda nada para quem chama a partir de Kotlin.
  • Um bloco de sincronização Java, que protege o cache de um objeto que não usamos, trocado por um bloco comum.
  • Uma chamada de formatação de texto na função que converte o tempo em texto, trocada por um preenchimento manual com zeros que dá a mesma saída.

Um script de patches que falha com barulho

Não editamos o arquivo à mão. Um pequeno script aplica cada mudança com uma expressão regular e confere quantas ocorrências espera. Se uma versão futura do motor mudar uma linha de lugar, o script para com erro em vez de produzir em silêncio um arquivo meio corrigido. O script também escreve no resultado um comentário de cabeçalho dizendo qual é a versão do motor, que só essas mudanças foram feitas e que o código de cálculo não foi tocado, o que mantém honesto o aviso de licença.

Atualizar o motor vira uma rotina repetível: baixar o código novo, rodar o script e rodar os testes.

Provando que nada mudou: testes dourados

Ninguém deveria confiar em uma migração só porque o compilador está feliz. Antes de migrar registramos a saída do código antigo do Android para um grande conjunto de casos: um resumo de leitura para cada signo durante mais de um ano de dias, amostras de texto completo, mudanças de signo da Lua, fases e datas de retrogradação, a semana ISO e os resultados de compatibilidade, além de um resumo criptográfico do banco de conteúdo. Depois da migração o código compartilhado precisa reproduzir esses arquivos exatamente.

E reproduz, e essa é a verdadeira rede de segurança. Quando o texto do banco de conteúdo muda de propósito, os arquivos dourados são regenerados com uma chave e a diferença é revisada como qualquer outra mudança.

O resto da migração

Em volta do motor valeram as trocas de sempre: as classes de tempo do Java viraram a biblioteca de data e hora do Kotlin, uma biblioteca JSON virou a serialização do Kotlin, e a formatação dependente do idioma virou pequenos auxiliares. Nada disso exigiu uma ideia engenhosa, só uma lista e paciência. O motor de astronomia foi a única dependência que precisou de um plano.

Perguntas frequentes

Por que não chamar uma biblioteca de astronomia nativa em cada plataforma?

Dois motores podem divergir um pouco nos horários das fases da Lua. Um único código-fonte compartilhado dá os mesmos resultados em todo lugar.

É permitido modificar uma biblioteca com licença MIT?

Sim, desde que o aviso de licença seja mantido. Nosso arquivo com patches o mantém e acrescenta um cabeçalho listando as mudanças.

O que acontece quando o motor publica uma versão nova?

Baixa-se o código novo e rodam-se o script de patches e os testes dourados. O script para se algum patch deixar de ser aplicado.

Como os testes dourados ajudam aqui?

Eles comparam o novo código compartilhado com a saída registrada do código antigo, então qualquer diferença em um resultado é detectada na hora.
