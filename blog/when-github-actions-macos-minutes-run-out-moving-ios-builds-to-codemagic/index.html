No macOS Minutes Left on GitHub Actions: Moving to Codemagic

By Nesim Razon, independent mobile developer · 2026-11-23

#iOS#Dev notes

I build my iOS apps from a Windows laptop, so every build runs on a rented Mac. For a while that Mac came from GitHub Actions. Then the free credit got close to empty and I moved new work to Codemagic. Here are the real numbers, the differences between the two pipelines, and the habits that keep the minutes from running out.

Why the quota matters: a minute is not a minute

On GitHub Actions the free allowance is money, not minutes. According to GitHub's billing docs, the Free plan includes 12 USD of compute per month for private repositories, and a macOS runner costs 0.062 USD per minute. A Linux 2-core runner costs 0.006 USD, so a macOS minute is about ten times more expensive. GitHub also rounds each job up to a whole minute.

Simple arithmetic: 12 divided by 0.062 is about 193 macOS minutes in a month. My first full day of experiments used 54 of them, which is 3.35 USD. By 14 November the credit was near 90 percent used, and I decided that new apps would build elsewhere.

The two pipelines side by side

  • GitHub Actions: file .github/workflows/ios.yml, runner macos-26, triggered by a push to the ios-kmp branch when iosApp, shared or the Gradle files change. Build number comes from github.run_number.
  • Codemagic: file codemagic.yaml at the repo root, instance type mac_mini_m2, started by hand from the web page (Start new build, branch main, pick the workflow). Build number is 1000 plus the Codemagic build number.
  • Both have two jobs: an unsigned simulator build for a quick check, and a TestFlight job that archives, signs and uploads.
  • Both have a time limit: 40 minutes for the simulator job and 60 for TestFlight (timeout-minutes in one, max_build_duration in the other).
  • Secrets: GitHub repository secrets in one, a Codemagic variable group named apple in the other. Both hold the same App Store Connect key id, issuer id and key text.

What a build costs on each side

A TestFlight run on GitHub took about six minutes in my setup, so roughly 0.37 USD. From 12 USD that is about 32 runs a month, if I did nothing else. On Codemagic my notes record builds of about 8 to 10 minutes.

Codemagic's pricing page says individuals get 500 free minutes per month on macOS M2 machines on a personal account, reset on the first of each month. Beyond that the page lists 0.095 USD per minute for the macOS M2 VM. At 8 to 10 minutes a build, 500 minutes is 50 to 60 builds. Slower per build, but a much bigger bucket for this workload.

Prices change. Check the current GitHub and Codemagic pricing pages before you plan around these numbers.

A worked example helps. Say a new app needs five failed runs before its first good TestFlight build, at about ten minutes each. This is an example, not a record of mine.

  • Credit on GitHub: 12 USD, about 193 macOS minutes.
  • One TestFlight run on GitHub: about 6 minutes, 0.37 USD.
  • Five failed runs plus one good run at 10 minutes: 60 minutes. On Codemagic that is 12 percent of the free 500.
  • On GitHub the same 60 minutes at 0.062 USD would be 3.72 USD, almost a third of the monthly credit.
  • The same 500 free Codemagic minutes at the pay-as-you-go rate of 0.095 USD would be 47.50 USD, so the free bucket is worth real money.

The point is that failures, not successes, decide how fast the bucket empties.

Moving a repo over: what changes

The simulator job moved almost unchanged: XcodeGen, then xcodebuild with CODE_SIGNING_ALLOWED=NO. The TestFlight job needed real changes, because Codemagic has its own signing tools.

The Codemagic job rebuilds the API key file, creates a keychain and fetches the signing files, then builds the ipa and publishes it:

  • keychain initialize
  • app-store-connect fetch-signing-files "com.example.app" --type IOS_APP_STORE --create
  • keychain add-certificates
  • xcode-project use-profiles
  • xcode-project build-ipa --project iosApp/iosApp.xcodeproj --scheme iosApp
  • app-store-connect publish --path build/ios/ipa/iosApp.ipa

The build number also needed care. In my setup the number in the package stayed at 1 until I wrote it straight into Info.plist with PlistBuddy after generating the project. The signing details have their own post on cloud signing certificates, and the build number has one too.

Mistakes that burned minutes

Most of my wasted minutes came from three mistakes, not from the price. Each one is cheap to avoid once you know it.

  • Cloud signing during the archive step created a new Apple Development certificate on every build. After about eleven the account hit its certificate limit and builds failed. The fix was one distribution key that I keep, fetched with the signing tools shown above.
  • The build number stayed at 1 for three attempts. Three runs, roughly thirty minutes, for one line in Info.plist.
  • A wrong Bundle ID chosen in the App Store Connect form made the upload fail with an altool error. You can check the Bundle ID through the App Store Connect API before any build, which costs zero macOS minutes.

The rule I took from this: anything that Windows or a web page can check goes before the Mac. A failed run costs the same as a good one.

Habits that save minutes

  • Run the Kotlin iOS compile on Windows first: the simulator target compiles locally and costs no macOS time.
  • Run a small pre-check script over the project before sending it, to catch the traps that already cost me runs.
  • On GitHub, limit the trigger with paths so a change to a README does not start a Mac.
  • Use a commit message marker. A commit containing [testflight] runs only the TestFlight job and skips the simulator job.
  • Use concurrency with cancel-in-progress, so a newer push cancels an older run.
  • On Codemagic, start builds by hand only. A push never spends minutes by accident.
  • Always run the simulator workflow first and the TestFlight one only when it passes.

Planning the month

My plan is simple. GitHub's credit renews at the start of the month, and so do Codemagic's 500 minutes. New apps and long port sessions go to Codemagic. GitHub keeps the older repos that already have a working workflow.

I count in builds, not minutes: about 8 to 10 minutes each, plus a spare allowance for the first run of a new app, when failures are most likely. If a month looks tight, I do more work on Windows and send fewer, better prepared builds.

There is no single winner. GitHub Actions is convenient when the code is already there: the workflow sits in the repo, secrets are in the repo settings and the build can start on every push. Its weak point for me is the dollar-based credit, because a macOS minute eats it ten times faster than a Linux one.

Codemagic suits a repo that builds iOS rarely and by hand. The minutes are a separate bucket of 500, and the signing tools are built for the TestFlight path. Its weak point is that you set up one more account, one more variable group and one more place for secrets.

If you build iOS a few times a week, either works. If you are porting several apps in the same month, count the builds first and choose the cheaper bucket.

Frequently asked questions

How much does a macOS minute cost on GitHub Actions?

GitHub's billing page lists 0.062 USD per minute for the macOS runner, against 0.006 USD for a Linux 2-core runner. Check the page for current prices.

How many free minutes does Codemagic give?

Its pricing page says individuals receive 500 free minutes per month on macOS M2 machines on a personal account, reset on the first of the month.

Are GitHub Actions minutes free for public repositories?

GitHub's docs say standard GitHub-hosted runners are free in public repositories. The credit I describe applies to private ones.

Can I keep both services?

Yes. I kept GitHub workflows in older repos and used Codemagic for new apps. Each repo uses one of them.
