Moving From GitHub Pages to Your Own Domain Without Losing SEO

By Nesim Razon, independent mobile developer · 2026-11-26

#Dev notes#Tools and calculators

My site started life on a github.io address, and in mid November 2026 I moved it to its own domain, nesimapps.com. The site is a static one, built by scripts, with four languages and a few hundred pages. This is the order I followed, what I checked after the switch, and the loose ends I only noticed because other systems depended on the old address.

Why move, and why not wait

A github.io address belongs to your account name, not to your project. Every link you collect, every store listing and every backlink points at a name you do not fully control. The site was only a few weeks old, which made the move cheap: there was very little history tied to the old address. That is the argument for doing it early.

Before switching I wrote down the real risks. The app stores had review pages that opened privacy and support URLs on the old address. After the switch those addresses would redirect, and the HTTPS certificate for the new name might take minutes to hours to appear. A reviewer landing in that window could see an error. The ad file, app-ads.txt, is also tied to the developer website listed in the stores. So I planned the switch for a quiet period, and I kept in mind that the whole change is reversible: removing the custom domain in the repository settings puts things back.

The order of operations

First I bought the domain and set up DNS, with the proxy turned off on every record. GitHub Pages wants to talk to the domain directly, and a proxy in front of it can get in the way of certificate issuing. The zone has the four address records and four IPv6 records that GitHub documents, a www record that points to the old github.io name, and the TXT record for domain verification. I verified the domain in GitHub first, two days before the switch, so nothing was left to chance on the day.

Second, before touching anything live, I made the base address a single constant in the site generators, so the switch could not leave a stray old address behind. Third, I entered the custom domain in the Pages settings. The repository then carries a CNAME file with one line, nesimapps.com. Fourth, I waited for the certificate and enabled the HTTPS enforcement. The publishing step takes a few minutes, and I polled the live site with a script instead of refreshing a browser.

The redirects come for free, but check them

Once a custom domain is set, GitHub Pages answers requests for the old github.io address with a permanent 301 redirect to the new domain, and it does the same for the www version of the new name. The path is kept. That matters more than it sounds, because my site also serves things that are not pages: the privacy policies, the app-ads.txt file and a small JSON file that older versions of my apps download. Those apps cannot be changed after they are published, and they keep working because the old URL still arrives at the new file.

I did not trust that and checked it. I requested the old privacy page, the ad file and the JSON file on the old address and confirmed each one ended on the new address with the same content. I also opened the www address. A redirect that goes to the home page instead of the matching path would be an easy mistake to miss, so I check the paths, not only the home page.

Canonical, sitemap and hreflang

A redirect alone is not enough. Search engines also read the signals inside your pages, and all of them have to say the new address. My site is built by a chain of generator scripts, and the last step splits it per language and adds the head tags. That step writes the canonical link, the alternate links for every language including the x-default entry, the language attribute and the structured data. It also writes the sitemap, which lists each page with its alternates and a last modified date, and the robots.txt file points at that sitemap. I rebuilt everything in one run with the new base address, so no page was left with a canonical on the old name.

The same change reached the machine-readable summary file for AI assistants, the QR code targets, the share cards and the script that posts articles to a developer community with a canonical link. The privacy and terms pages stay out of the sitemap and carry a noindex tag, as before. After publishing I opened a few pages from each language on the live site and read the head tags, and I fetched the sitemap itself, because a sitemap that still lists the old host is the classic leftover.

Search Console, Bing and the other accounts

In Search Console I used a domain property, verified through DNS. A domain property covers the www and non-www names and both protocols, so it fits a site that will always be reached through redirects from other forms of the address. My reporting script reads search data through the API with a service account, and that account has to be added to the new property as a restricted user, or the report comes back empty. I added it and kept the old property as a fallback in the script until I deleted it shortly after. The history I had already saved in my own archive stayed there, because Search Console only keeps sixteen months and I never relied on it for the past.

Bing Webmaster got the new site and its sitemap. Yandex needed its two verification files in the site root. The instant-indexing workflow that pings search engines when pages change got the new host. For analytics I updated the stream address, and the tracking script accepts both host names, so a visit that somehow lands on the old name is still counted instead of dropped. The web stats script for my dashboard looks for the new property first. Bing data was empty for the first few days on the new site, which I expected.

app-ads.txt, store listings and UTM

The ad file lives at the root of the site, and ad networks find it through the website you list in the store. On Android that field is in the Play Console, and I changed it, along with the privacy policy address on every app, to the new domain. On iOS the stores read the marketing and support URLs from App Store Connect, and those are separate fields that someone has to change by hand.

That was the loose end. The day after the move, an ad verification for an iOS app was stuck, and the public App Store pages still showed the old github.io addresses. My working explanation is that the verifier starts from the old address and follows a redirect to another domain, which it may not accept. I have not proven that. The fix I wrote down is to enter the new domain in App Store Connect, then ask the ad network to check again. I mention it because it shows how a move touches systems that never appear in your repository.

For UTM tags I made a deliberate choice. The Play links on the site carry a referrer with utm_source set to the old name. I left it unchanged so that months of earlier data and new data stay in one series. The only thing that would force a change is a source-based filter, and I plan to look at GA4 two weeks later to see whether sessions still arrive with the old host as the source.

The checklist I would reuse

  • Verify the domain with the hosting provider before you switch, and keep the DNS proxy off.
  • Put the base address in one constant and rebuild everything in a single pass.
  • Check the redirects on real paths: policies, ad file, data files, language folders and www.
  • Read canonical, alternates and the sitemap on the live site, not only in the source.
  • Add the service account to the new search property before you need the data.
  • List every outside system that stores your address: store listings, ad file checks, profiles, article cross-posts.

What I cannot tell you

I do not have a before-and-after traffic story for this move, and I will not invent one. The site was young, my search data is small and the numbers move for many reasons at once. What I can show is that the technical signals were consistent on the day I switched, and that the redirect paths worked. If you do this, write down your own baseline first and look again after a few weeks.

Frequently asked questions

Does GitHub Pages redirect the old address automatically?

Yes. After you set a custom domain, requests to the old github.io address are redirected with a 301 to the new domain, and the path is kept. Check a few real paths to be sure.

Should I use a domain property in Search Console?

It is a good fit for a moved site, because it covers www, non-www and both protocols. It is verified through a DNS record.

Why keep the DNS proxy off with GitHub Pages?

GitHub Pages issues the HTTPS certificate for your domain and wants to reach it directly. A proxy in front can interfere with that process.

Can I undo the move?

Yes. Removing the custom domain in the repository settings returns the site to the github.io address, which is why a quiet period is enough for the switch.

Will app-ads.txt keep working after a move?

It is read from the website you list in each store. Update that field in every store, and check the ad network's verification status afterwards.
