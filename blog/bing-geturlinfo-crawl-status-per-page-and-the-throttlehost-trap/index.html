Bing GetUrlInfo: Crawl Status per Page and ThrottleHost

By Nesim Razon, independent mobile developer · 2026-11-28

#Dev notes#Tools and calculators

My reporting script already asked Google, page by page, which addresses of my site were in the index. A reader's comment made me ask the same question about Bing. The Webmaster API has a method for it, but the answer is narrower than I expected, and my first fast attempt got my requests blocked for hours.

What GetUrlInfo returns

GetUrlInfo is a method of the Bing Webmaster API. You send your API key, the site address as it is registered in the tool and one page address. The answer describes what Bing knows about that single page.

For my purpose two fields matter: the date Bing discovered the address and the date it last crawled it. An address Bing has never seen does not produce an error. It comes back with a placeholder date, the first of January of the year one. If you parse dates without thinking about this, an unknown page looks like a page that was discovered a very long time ago.

So the script turns every answer into one of three states. Crawled means there is a real last crawl date. Discovered means there is a discovery date but no crawl yet. Unknown means neither date is real.

Crawled is not the same as indexed

This is the most important limit, and it is easy to blur. Google's URL Inspection API gives a verdict about the index. GetUrlInfo does not. It tells you whether Bing fetched the page, not whether the page can appear in results.

The inspection screen inside the Bing Webmaster panel shows more detail, but that detail is not in this method. In my dashboard I therefore label the column honestly: crawled is the closest signal available, not proof of indexing. If you mix the two in one chart, you will believe your Bing coverage is better than you actually know.

A separate earlier post on this site covers another surprise of the same API, report methods that return empty lists while the web panel shows data. It is worth reading before you build anything on top of these calls.

The trap: one request per page, and not too fast

There is one request per page. A site with a few hundred addresses, counting four languages, needs a few hundred calls. The natural reaction is to run them in parallel. I did that with eight workers.

The block arrived immediately. The API answered with HTTP status 400 and a body carrying error code 5, named ThrottleHost. It did not clear after a few seconds. It lasted for hours, which also means that retrying in a loop while you debug is the worst thing you can do.

I could not find a published number I could rely on for the allowed rate, so the settings below come from caution rather than from a documented limit.

The settings that work for me

  • One request at a time, never in parallel.
  • A pause of about 1.2 seconds between calls.
  • At most 150 pages in one run.
  • When the response mentions throttling, wait 30 seconds before the next page.
  • After three throttled answers in a row, end the run. The progress is already saved.

A cache makes the small batches fine

A batch limit sounds like a problem when the site has more pages than the limit. It is not, because results are cached in a local file, one entry per address, with the date it was checked. The next run only asks about entries that are old enough.

Old enough depends on the state. A page that is already crawled changes rarely from my point of view, so it is refreshed only weekly. A page that is only discovered, or unknown, is checked again after a day, because that is where I am waiting for a change.

The whole site fills in over a few runs. Since the report runs anyway, this costs me nothing but patience.

Ask about the interesting pages first

With a limited budget per run, order matters. The script first takes the addresses that Google does not have in its index. That is the actual question: is a page missing only in one search engine, or in both? After those come pages that were never checked, then the ones checked longest ago.

This turns two separate lists into one table. For each page that Google has not indexed, I can see whether Bing has crawled it, found it or never heard of it. A page that neither of them has touched points to a discovery problem such as weak internal links. A page Bing crawled and Google skipped is a different conversation, usually about whether the page adds something.

These are hints for where to look, not conclusions. Two crawlers behave differently, and a small site has very little data.

Group by language

My site publishes most pages in four languages, with English at the root and the others under their own folders. The script reads the first folder of each address and counts, per language, how many pages exist and how many Bing has crawled.

A single total would hide a language that lags far behind. Per language numbers show it at once, and they are cheap, because they come from the same cached data.

Errors that are not throttling

Not every failed call is a rate limit. A timeout or a broken answer can happen to any single request. My script does not treat those as results: nothing is written to the cache for that address, so the next run sees it as stale and asks again. Writing a guessed state would be worse than writing nothing, because the report could not tell a real unknown from a failed request.

The throttle case is handled separately because it is not about one address. It is about all following calls. That is why it counts consecutive answers: one throttled reply may be noise, three in a row mean the service wants me to stop. A successful answer resets the counter.

Keeping my own noindex pages out of the problem list

Before comparing the two engines, the list of missing pages has to be honest. Some pages may be marked noindex on purpose, and counting them as a failure sends you hunting for a bug that is a decision. The Google side of my report stores the indexing state that URL Inspection returns and recognises when a page is excluded by a robots tag or header.

Those pages leave the list of missing pages and get their own counter. At the moment I built it, my sitemap had no such page, but the rule is cheap and stops the report from raising false alarms later. The general advice is to separate three things: not found yet, seen and not indexed, and excluded because you asked for it.

What I do with the result

The numbers are only useful if they lead to an action I can take. For a page neither engine has visited, I check that other pages of the site actually link to it and that it is in the sitemap. For a page Bing crawled and Google did not index, I reread the page and ask whether it says something the neighbouring pages do not.

I avoid reacting to a single day. Crawlers come back on their own schedule, so I compare the picture across several reports before changing anything, and I change one thing at a time so I can tell what made a difference.

What I would check before copying this

  • Is the site address exactly the one registered in Bing Webmaster Tools?
  • Is the API key kept outside the repository?
  • Does your date parser treat the year one placeholder as no date?
  • Can the script be stopped at any moment without losing finished work?
  • Does the report say crawled rather than indexed?

Frequently asked questions

Does GetUrlInfo tell me whether a page is indexed by Bing?

No. It gives discovery and crawl dates. Crawled is a useful signal but not a verdict about the index.

What does an unknown URL look like in the response?

The dates come back as a placeholder, the first of January of year one, instead of an error.

What is the ThrottleHost error?

An HTTP 400 answer with error code 5, returned when requests arrive too quickly. In my case it lasted for hours.

How fast can I call GetUrlInfo?

I send one request about every 1.2 seconds with at most 150 per run. That is a cautious choice of mine, not a documented limit.
