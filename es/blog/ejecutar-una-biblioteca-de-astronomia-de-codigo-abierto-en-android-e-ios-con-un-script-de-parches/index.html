Astronomía de código abierto en Android e iOS con un script de parches

Por Nesim Razon, desarrollador móvil independiente · 2026-11-18

#Notas de desarrollo#Astronomía#iOS

Nuestra app de horóscopo y Luna necesita astronomía de verdad: dónde está la Luna, cuándo cambia la fase, cuándo parece que un planeta retrocede. Para eso usamos un motor de código abierto, y funcionaba en Android. Cuando pasamos la app a Kotlin Multiplatform para iPhone, el motor no vino con nosotros. Así lo hicimos funcionar en ambas plataformas sin cambiar un solo cálculo.

El problema: un artefacto solo para JVM

El motor se publica como una biblioteca de Kotlin, y la versión ya hecha del repositorio central de Maven funciona solo en la máquina virtual de Java. Eso va bien en Android y no sirve en el código compartido, que también debe compilar para iPhone. No queríamos reescribir miles de líneas de matemática orbital, ni llamar a una biblioteca distinta en cada plataforma, porque dos motores pueden dar horas de fases lunares ligeramente distintas.

Usar el código fuente, no el paquete

El motor es de código abierto con licencia MIT y entero está en un único archivo fuente de Kotlin. Así que en lugar del paquete tomamos el propio archivo fuente y lo pusimos en el conjunto de fuentes común del módulo compartido. La pregunta pasó a ser qué hay de específico de Java en ese archivo. Resultó que muy poco.

Qué hubo que cambiar

  • Una anotación a nivel de archivo que fija el nombre de la clase Java, que el código común no conoce.
  • Unas pocas anotaciones que hacen estáticas las funciones o generan sobrecargas de Java, de nuevo solo de Java. Quitarlas no cambia nada para quien llama desde Kotlin.
  • Un bloque de sincronización de Java, que protege la caché de un objeto que no usamos, sustituido por un bloque normal.
  • Una llamada de formato de texto en la función que convierte el tiempo en texto, sustituida por un relleno de ceros manual con el mismo resultado.

Un script de parches que falla con ruido

No editamos el archivo a mano. Un pequeño script aplica cada cambio con una expresión regular y comprueba cuántas coincidencias espera. Si una versión futura del motor mueve una línea, el script se detiene con un error en lugar de producir en silencio un archivo a medio parchear. El script también escribe en el resultado un comentario de cabecera que dice qué versión del motor es, que solo se hicieron estos cambios y que el código de cálculo no se tocó, lo que mantiene honesto el aviso de licencia.

Actualizar el motor se convierte en una rutina repetible: descargar el código nuevo, ejecutar el script y ejecutar las pruebas.

Demostrar que nada cambió: pruebas doradas

Nadie debería fiarse de una migración solo porque el compilador esté contento. Antes de migrar registramos la salida del código antiguo de Android para un gran conjunto de casos: un resumen de lectura para cada signo durante más de un año de días, muestras de texto completo, cambios de signo de la Luna, fases y fechas de retrogradación, la semana ISO y los resultados de compatibilidad, además de un resumen criptográfico del banco de contenido. Tras la migración el código compartido debe reproducir esos archivos exactamente.

Lo hace, y esa es la verdadera red de seguridad. Cuando el texto del banco de contenido cambia a propósito, los archivos dorados se regeneran con un interruptor y la diferencia se revisa como cualquier otro cambio.

El resto de la migración

Alrededor del motor se aplicaron los reemplazos habituales: las clases de tiempo de Java pasaron a la biblioteca de fecha y hora de Kotlin, una biblioteca JSON pasó a la serialización de Kotlin, y el formato dependiente de la configuración regional pasó a pequeñas funciones auxiliares. Nada de eso exigió una idea ingeniosa, solo una lista y paciencia. El motor de astronomía fue la única dependencia que necesitó un plan.

Preguntas frecuentes

¿Por qué no llamar a una biblioteca de astronomía nativa en cada plataforma?

Dos motores pueden diferir un poco en las horas de las fases lunares. Un solo código fuente compartido da los mismos resultados en todas partes.

¿Está permitido modificar una biblioteca con licencia MIT?

Sí, siempre que se conserve el aviso de licencia. Nuestro archivo parcheado lo mantiene y añade una cabecera que enumera los cambios.

¿Qué pasa cuando el motor publica una versión nueva?

Se descarga el código nuevo y se ejecutan el script de parches y las pruebas doradas. El script se detiene si algún parche ya no se aplica.

¿Cómo ayudan aquí las pruebas doradas?

Comparan el nuevo código compartido con la salida registrada del código antiguo, así que cualquier diferencia en un resultado se detecta al instante.
